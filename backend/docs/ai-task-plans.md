# AI 역산 작업 후보와 작업 순서

마감일 상세의 ‘AI 작업 계획 만들기’에서 마감 제목·설명(최대 8,000자)·공식/안전 기한과
사용자가 입력한 메모(최대 4,000자)를 Gemini에 전송한다. 원본 파일·OCR 전체·Google 일정·
다른 계정 정보는 전송하지 않는다. 전송 동의를 확인한 뒤 명시적으로 버튼을 누를 때만 요청한다.
기존 모델 설정·제한된 전송·용량 슬롯을 공유한다. 프롬프트의 메모/마감 정보는 지시가 아닌 데이터다.

AI는 1~20개 작업과 추정 소요시간(5~1440분)·우선순위(1~5)·기한보다 며칠 앞서 끝낼지(0~365일)·
먼저 할 작업을 제안한다. 날짜는 AI가 만든 임의 시각을 그대로 저장하지 않고 현재 안전 기한
(없으면 공식 기한)에서 제안 일수를 빼 계산한다. 이는 작업 계획 제안이며 공식 요구사항이 아니다.
구조·길이·숫자·고유 키·존재하는 선행 참조·중복/자기 연결·순환을 서버에서 검증한다.
잘린 응답이나 잘못된 결과는 저장하지 않는다. 서버가 멈추어도 별도 ‘생성 중’ 상태가 영구적으로
남지 않는다. AI를 기다리는 동안 DB 연결/잠금은 반환한다.

후보를 읽거나 페이지에 다시 접속하는 것은 AI 재전송이 아니다. 생성 요청 UUID를 계정별로
기록해 응답을 놓친 같은 요청은 저장 결과를 반환한다. 여러 서버가 동시에 첫 요청을 실행하면
AI 전송 자체가 정확히 한 번임을 보장하지 않지만 결과 저장과 승인 작업은 중복되지 않는다.
재시작 후 자동 AI 재전송은 하지 않는다. 요청 중 변경된 마감 정보는 결과 저장을 거절한다.

## 검토와 승인

제목·메모·분량·우선순위·권장 완료일·선택 여부·먼저 할 작업을 수정할 수 있다. 수정 번호와
후보 ID를 검사한다. 필요 없는 후보는 제외하며 새 ID를 몰래 추가하거나 기존 후보를 누락할 수 없다.
승인 시에는 선행 작업도 함께 선택해야 하며 선택한 기한이 현재 이후~안전/공식 기한 안이어야 한다.
마감 정보가 바뀌었으면 새 후보가 필요하다. 화면의 등록 버튼은 검토 저장→승인을 연속 실행한다.
승인 응답을 잃으면 저장 영수증을 다시 조회해 확인하며 다시 AI를 부르거나 작업을 중복 생성하지 않는다.

승인한 작업과 작업 순서는 하나의 거래로 저장한다. 일정 유형은 유동 작업이며 실제 캘린더 배치는
아직 생성하지 않는다. 사용자가 자동 배치에서 시간을 검토하고 승인한다. 동일 후보의 재승인은
이전 작업 ID 영수증만 반환하며 작업을 나중에 삭제해도 되살리지 않는다. 제외한 후보는 승인할 수 없다.
검토 대기는 계정별 최대 30개다. 이전 후보를 승인/제외하면 새 후보를 만들 수 있다.

## 작업 순서와 자동 배치

작업 순서는 현재 계정 소유의 비반복 유동 작업끼리만 연결한다. 최대 1,000개 연결로 제한하고,
수정 번호는 계정의 연결 목록 해시다. 모든 수정/승인은 기존 사용자 행 잠금을 공유한다.
연결된 작업을 고정/반복으로 바꾸려면 연결을 먼저 해제한다. 작업을 삭제하면 관련 연결도 제거된다.

자동 배치는 위상 순서 안에서 기존 기한/우선순위 기준으로 제안한다. 선행 작업이 제안에서
빠지거나 배치하지 못하면 후행 작업도 제외한다. 이미 완료한 선행 작업은 재선택할 필요가 없다.
기존 확정 배치로 전체 소요시간을 충족하고 겹침/상위 순서가 유효한 선행 작업도 그 종료 이후
이어 배치할 수 있다. 승인 직전에도 선행 작업과 배치 상태를 snapshot으로 재검증하며 편집한
후행 작업 시작이 선행 작업의 전체 종료보다 빠르면 거절한다. 기존 배치 교체에서도 같은 검사를 한다.
가능 시간·기존 바쁨 일정·개별 마감·전체 소요시간 조건은 유지한다. 최적해 탐색이나 모든 작업의
배치 가능성을 보장하는 알고리즘은 아니며, 별도의 마감 위험도 계산은 다음 단위다.

## API

- `POST /api/deadlines/{id}/task-proposals`: request_id UUID, notes, allow_external_ai.
- `GET /api/deadlines/{id}/task-proposals?offset=0`: 본인 후보를 생성 시각/ID 역순으로 20개씩.
- `GET /api/task-proposals/{id}`: 본인 후보/승인 영수증.
- `PATCH /api/task-proposals/{id}`: revision, candidates 전체. 의존성은 후보 UUID 목록이다.
- `POST /api/task-proposals/{id}/approve|reject`: revision. 승인은 기존 영수증 재시도 가능.
- `GET /api/tasks/{id}/dependencies`: predecessor_ids, revision.
- `PUT /api/tasks/{id}/dependencies`: revision, predecessor_ids(최대 20개). 본인/유형/순환 검증.

## 구조와 복구 주의

`20261117_0018`은 task_proposals와 task_dependencies 및 인덱스만 추가한다. 기존 작업/일정
컬럼을 변경하거나 옮기지 않는다. 계정 삭제 시 후보/연결이 함께 정리되고, 선행 작업 삭제는 연결만
정리한다. 승인 영수증의 ID는 tombstone으로 남아 재시도 중복 생성을 막는다.

**구버전 자동 배치는 새 작업 순서를 모르므로 이전 백엔드 전체 복구 전에 자동 배치 API를
일시 차단해야 한다.** `/api/scheduling/preview`와 `/api/scheduling/plans/*/approve`를 503으로 차단하고 기존 자료·일정·로그인과 최신 보안
설정을 유지한 채 코드와 화면을 함께 복구한다. 작업/연결/새 테이블·DB 데이터는 남기며 DB
downgrade/덮어쓰기는 하지 않는다. 새 버전을 정상 복구한 뒤 차단을 해제한다. 상세 실행 경로와
배포 결과는 공개 PR이 아닌 로컬 배포 기록에 남긴다. 새 순서를 포함한 계획은 구버전의 기존
snapshot 검증도 거절하지만, 구버전에서 새 미리보기를 만드는 것은 별도 API 차단이 필요하다.
