# 잡코리아 남은 기간과 마감일 검토

공개 잡코리아 채용공고 URL을 기존 자료 추출 → HTML 마감일 검토 → 사용자 승인
흐름으로 등록합니다. Gemini 호출, JavaScript 실행, 로그인 우회는 하지 않습니다.
승인 전에는 마감일을 생성하지 않습니다.

## 추출 근거

- 대상은 `jobkorea.co.kr` 또는 `www.jobkorea.co.kr`의
  `/Recruit/GI_Read/{공고번호}` 페이지입니다.
- 동일 공고로 검증된 JSON-LD `JobPosting`과 HTML의 `Countdown` 표시가 있어야 합니다.
  HTML에 포함된 Next Flight JSON 중 `남은기간` 바로 옆 타이머의 `endDate`만 읽습니다.
  스크립트는 실행하지 않고 제한된 JSON 데이터만 해석합니다.
- 추천 공고의 `applyCloseDate`나 다른 위치의 `endDate`는 사용하지 않습니다.
  `0일 14:40:59`처럼 남은 시간만 있으면 수집 시각을 더해 날짜를 만들지 않습니다.
- 타이머의 일시는 초와 시간대가 명시되어야 합니다. 같은 공고의 `validThrough`와
  날짜·시각을 대조하며, 메타데이터가 분 단위면 같은 분의 명시된 초를 허용합니다.
  메타데이터도 초 단위면 정확히 일치해야 합니다. 날짜만 있으면 한국 날짜를 대조합니다.
- 타이머가 여러 개이거나 메타데이터와 충돌하면 후보 마감일을 비우고 사용자 확인을
  요청합니다. 지원하는 타이머 데이터가 없으면 기존 HTML 날짜 검토로 돌아갑니다.
- 최대 128개 Flight 데이터 블록, 합계 200,000자, JSON 컨테이너 4,096개,
  중첩 32단계로 제한합니다. 기존 URL 접근·robots·응답 크기 제한도 유지합니다.

2026-10-27에 사용자 제공 공고 `50195748`을 실제 추출 절차로 확인했습니다.
HTML 표시 영역은 빈 타이머였지만 같은 응답의 타이머 데이터에는
`2026-10-27T23:59:59+09:00`, 같은 공고 메타데이터에는 `2026-10-27T23:59`가
있었습니다. 초를 버리지 않고 전자를 후보로 사용합니다. 공고 내용은 이후 바뀔 수 있습니다.

## 응답과 화면

기존 AnalysisResponse의 `source_period`에 `site: "jobkorea"`가 추가됩니다.
기존 사람인 응답은 `site: "saramin"`이며, 과거 응답의 `site` 생략도 프론트엔드에서
사람인으로 처리합니다. 새로운 API 경로, 환경변수, DB 변경은 없습니다.

검토 화면은 잡코리아 원문 마감일과 현재 남은 기간을 표시합니다. 남은 기간은
확정된 원문 마감일과 기기의 현재 시각으로 매초 계산하며 별도 요청을 보내지 않습니다.
추출 당시 타이머를 현재 값처럼 표시하지 않습니다. 사용자가 제목만 수정해도 원래
일시의 초·시간대를 유지합니다. 승인 후에는 기존 중복 승인 방지와 원문 변경 검사를
적용하며 Task나 Google Calendar 이벤트를 생성하지 않습니다.

이전에 추출한 자료와 분석은 변경하지 않습니다. 새 근거를 반영하려면 자료를 다시
추출하고 새 검토를 시작해야 합니다. 백엔드와 프론트엔드 코드 모두 반영해야 새 표시가
동작합니다.

## 검증

`tests/test_jobkorea_period.py`는 분리된 SQLite에서 공고 식별, 조각난 Flight 데이터,
추천 공고 제외, 상대 시간·잘못된 날짜·충돌, JSON 해석 제한, 승인·중복 승인을 검사합니다.
SQLite는 시간대 오프셋을 보존하지 않으므로 DB 삽입 직전 값의 시각·오프셋도 검사합니다.
운영 PostgreSQL/RDS 데이터는 테스트에서 사용하지 않습니다.

`frontend/tests/remaining-period.spec.ts`는 PC·모바일에서 잡코리아 표시, 매초 갱신,
제목 수정 시 초 보존, 승인 후 새로고침, 가로 넘침을 확인합니다. 브라우저 테스트만
가상 응답을 사용하며 운영 코드에는 가상 결과가 없습니다.
