# PlanCatch 내부 캘린더

현재 Scheduled Event CRUD 계약으로 직접 지정한 배치 시간을 관리합니다. Task의 가능 기간과 Deadline의 마감일을 배치 시간으로 간주하지 않습니다. 백엔드·배포 설정 변경이나 추가 환경변수 없이 기존 `NEXT_PUBLIC_API_BASE_URL`과 Bearer 인증을 사용합니다.

## 사용 흐름

1. 수동 일정을 저장하거나 기존 일정 상세를 엽니다.
2. **캘린더 배치 → 캘린더에 배치**에서 시작·종료 시간을 확인합니다. Task의 가능 기간은 초기 입력값으로만 사용하며 날짜가 없으면 직접 입력합니다.
3. 제출 시 `POST /api/scheduled-events`로 `task_id`, `start_at`, `end_at`, `status: approved`만 보냅니다. Task 저장과 배치를 하나의 원자적 요청처럼 가장하지 않으며 배치 실패로 Task를 다시 생성하지 않습니다.
4. 사이드바 또는 대시보드에서 `/calendar`를 엽니다. 월간·주간 날짜 선택, 선택 날짜의 배치 목록, 이전/다음 기간·오늘·날짜 이동을 지원합니다.
5. 일정 상세의 배치 내역에서 시간·상태(확정/제안/취소)를 수정하거나 배치만 삭제합니다. 삭제 확인·취소를 제공하며 연결된 Task의 가능 기간과 내용은 유지합니다.

Task 내용/가능 기간 수정은 배치 시간을 자동 변경하지 않습니다. 한 Task의 여러 배치를 허용합니다. 캘린더는 실제 Scheduled Event만 표시하며 마감일·미배치 Task를 임의의 시간에 넣지 않습니다.

## 날짜·목록·오류

- 날짜 계산·표시는 `Asia/Seoul` 기준입니다. UTC ISO 8601의 `start_from`·`end_before`로 서버의 반열린 구간 겹침 조회를 사용합니다. 자정에 끝나는 배치를 다음 날짜에 중복 표시하지 않고 변경하지 않은 배치 날짜의 초·밀리초를 보존합니다.
- 100건 페이지를 최대 20회 조회합니다. 제한에 닿으면 첫 2,000건만 표시했다는 안내를 제공하고 주간 보기로 범위를 줄일 수 있습니다. 실패를 빈 캘린더로 표시하지 않습니다. 선택 날짜 목록은 20건씩 넘겨 보며 연결 Task에서 제목을 조회합니다. 제목 조회 실패는 별도로 알리고 배치를 숨기지 않습니다.
- 제안·확정·취소·동기화 상태는 서버 응답대로 구분합니다. 취소는 기본 숨김이며 체크박스로 포함합니다. `synced` 또는 `google_event_id`가 있는 배치는 수정·삭제를 제공하지 않습니다. 기존 데이터 표시가 Google 연동 구현을 의미하지 않습니다.
- 저장 중 중복 제출을 막고 오류 시 입력을 유지합니다. 생성의 연결 오류 또는 5xx로 저장 여부가 불확실하면 자동 재시도하지 않고 제출을 잠급니다. **배치 내역 다시 불러오기**에서도 입력을 유지합니다. 새 요청은 내역 확인 후 폼을 닫고 다시 시작해야 합니다.
- 401은 기존 로그인 만료 처리, 404는 삭제·접근 불가/API 미제공 안내, 409는 동기화 일정 변경 제한 안내를 제공합니다. 기타 422/429/503 등도 가짜 결과 없이 표시합니다.

## 후속 기능

자동 배치·재배치·시간 겹침/마감일 충돌 검사·역산 계획, Google 계정 연결·Calendar 전송·동기화, 반복·하루 종일 일정, 드래그 시간 변경은 구현하지 않습니다. PDF·JPG 업로드와 추출도 별도 작업입니다.

현재 API에는 겹침이나 Task/Deadline 범위 검사가 없으므로 그 검사를 보장하지 않습니다. 원클릭 Task/배치 등록과 불확실한 응답의 안전한 자동 재시도에는 트랜잭션·idempotency 계약이 필요합니다. 자동 배치와 Google 연동은 해당 백엔드 API가 준비된 뒤 진행합니다.

## 검증과 운영 확인

lint·TypeScript·프로덕션 빌드를 통과했습니다. PC·모바일 126개 시나리오를 검증했습니다. 첫 실행에서 124건이 통과했고, Next.js 페이지 안내 영역과 오류 안내를 구분하도록 2개 오류 처리 테스트의 선택자를 수정한 뒤 두 시나리오도 통과했습니다. 브라우저 응답은 `tests/calendar.spec.ts`와 분리된 `tests/calendar-fixtures.ts`를 사용합니다. 월/주 화면도 직접 확인했습니다.

운영 서버의 `/health` 200과 비인증 배치 API 401을 확인한 뒤, 새 프론트엔드의 로컬 프로덕션 빌드를 운영 API에 연결한 실제 브라우저 검증 1건(PC)을 수행했습니다. 임시 전용 계정을 생성해 Task 등록 → 배치 생성 → 캘린더 조회·새로고침 → 배치 수정 후 재조회 → 가능 기간 유지 확인 → 취소·포함 표시 → 배치 삭제 후 Task 유지까지 통과했습니다. 생성한 배치와 Task는 정리하고 404도 확인했습니다. 계정 삭제 API가 없어 데이터가 비어 있는 테스트 계정 1개는 남습니다. 기존 사용자 자료는 조회·변경하지 않았습니다.

이 검증은 운영 웹사이트에 새 화면을 배포했다는 뜻이 아닙니다. 운영 반영 후 메뉴·경로를 한 번 더 확인해야 합니다. 계정 비밀번호·Bearer 토큰은 런타임에서만 사용하며 출력·trace/HAR/video/screenshot/Git에 저장하지 않습니다. 기존 사용자 자격 정보를 요청하지 않습니다.

실제 서버 검증은 `PLANCATCH_LIVE_API_URL`을 설정한 후 `npm run test:live -- calendar.spec.ts --project=desktop`으로 명시적으로 실행합니다. 테스트 데이터는 `[테스트] Codex 캘린더` 접두어로 표시합니다. 이 시나리오는 AI 서비스나 Google API를 호출하지 않습니다.
